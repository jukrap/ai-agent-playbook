# Rendered review

Compare the same viewport, data, and interaction state. Start with user impact rather than an aesthetic score.

- Can the primary action and important information be found quickly?
- Does density support the workflow and content size?
- Are hierarchy, spacing, text fit, scrolling and responsive priorities stable?
- Do keyboard navigation, focus, labels, contrast and reduced motion work where relevant?
- Are loading, empty, error and disabled states legible without color alone?

Cards, pills, shadows, gradients and rounded corners can be appropriate. Repetition is a defect only when it obscures hierarchy, wastes working space, hides information, or conflicts with an actual product constraint.

Example: keep brand-colored pills for three meaningful statuses; remove repeated decorative pills that push table actions below the fold. Preserve a useful card boundary instead of flattening every panel.

A static scan may locate candidates. Confirm them in rendered output before changing the design. Report named viewports and states actually inspected; screenshots alone do not prove keyboard behavior. Reuse the project's browser/test tools instead of introducing another toolchain for one small edit.

Code-structure cleanup and prose editing are separate tasks. Review UI copy here only when it changes task clarity or specificity.
