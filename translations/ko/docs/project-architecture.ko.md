# 프로젝트 아키텍처를 정하고 바꾸는 방법

AAPB는 프레임워크 이름만으로 소스 코드 구조를 정하지 않습니다. React 프로젝트도 라우트 중심, 기능 중심, FSD 등 상황에 맞는 구조를 사용할 수 있습니다. 한 저장소 안에서도 애플리케이션마다 다른 경계가 필요할 수 있습니다.

모델은 주어진 근거를 보고 구조를 제안할 수 있습니다. 그래도 배포 단위, 호환성, 데이터 관리 주체, 팀의 담당 범위와 예상 변화는 프로젝트에서 알려줘야 합니다. 이후 작업이 지켜야 할 결정을 기록하세요. 작은 변경마다 완성된 폴더 트리나 이름 붙은 아키텍처가 필요한 것은 아닙니다.

## 어디에 무엇을 적나요?

| 위치 | 적을 내용 |
| --- | --- |
| 개인 전역 AGENTS.md | 대화·협업 방식과 공통 검증 선호 |
| 프로젝트 AGENTS.md | 적용할 프로젝트 규칙, 확인된 명령과 채택한 아키텍처 링크 |
| 기존 아키텍처·명세·결정 문서 | 적용 범위, 모듈 역할, 의존성 방향, 공개 인터페이스, 예외와 이유 |
| CURRENT.md | 현재 목표, 관련 아키텍처 결정 링크와 다음 단계 |
| import, package exports, 테스트나 기존 경계 검사 | 구현이 결정한 규칙을 따르는지 확인할 근거 |

목적에 맞는 기존 문서가 있으면 사용합니다. 같은 결정을 ARCHITECTURE.md, FSD.md와 ADR에 반복해서 만들지 않습니다. 이 안내의 파일명은 예시이며 필수 파일이 아닙니다.

## 기존 프로젝트

관련 지침과 현재 코드를 읽고 구조를 판단합니다. 변경에 관련된 공개 import, 라우트, 빌드 단위, 상태 관리 주체와 테스트를 확인하세요.

- 일반 기능 추가나 오류 수정은 채택한 경계 안에서 진행합니다. 새 템플릿을 받았다는 이유로 저장소 전체를 재배치하지 않습니다.
- 코드와 채택한 설계가 다르면 차이를 알립니다. 코드는 현재 구현의 근거이며 의도한 설계를 자동으로 폐기하는 기준은 아닙니다.
- 구조 이전이 허용된 작업이면 바꿀 경계, 호출부의 전환, 임시 호환 방법과 검증을 정합니다. 의미 있는 일부를 이전한 뒤 범위를 넓힙니다.
- 구조가 문서화되지 않았다면 이번 작업에 중요한 제약부터 적습니다. 빠진 결정이 목표, 담당 범위나 호환성을 크게 바꿀 때만 질문합니다.

## 새 프로젝트

넓은 범위의 구현에 들어가기 전에 제품의 형태를 파악하고 요청 범위에 맞는 출발 구조를 고릅니다. 작은 앱은 라우트와 역할이 분명한 몇 개 모듈로 충분할 수 있습니다. 담당 범위, 재사용이나 배포 문제를 해결할 때 경계를 추가합니다.

다음 내용을 남깁니다.

1. 프로젝트의 어느 부분에 적용하며 어떤 문제를 해결하는지.
2. 동작, 데이터와 공개 인터페이스를 어느 모듈이 담당하는지.
3. 어떤 의존성을 허용하고 어떤 내부 구현을 숨길지.
4. 알려진 예외, 그 이유와 예외를 없앨 조건.
5. 경계를 확인할 근거와 이 결정을 다시 검토할 조건.

허용된 구현 안의 일상적인 선택마다 별도 승인 절차를 만들 필요는 없습니다. 프로젝트에서 명시적으로 승인을 요구하면 그 규칙을 따릅니다. 아직 제안인 내용을 이미 채택한 요구사항처럼 적지는 않습니다.

## FSD는 선택지 중 하나입니다

FSD는 프론트엔드 애플리케이션의 경계를 정하는 선택지입니다. 모든 React/Vite 저장소나 백엔드의 기본값은 아닙니다. [공식 개요](https://feature-sliced.design/docs/get-started/overview)도 app, pages, shared만 사용하는 작은 예시와 점진적 도입을 설명합니다. 선택한 설계에 필요한 계층을 사용하고 그림을 맞추려고 빈 계층을 만들지 않습니다.

FSD를 채택했다면 적용 범위와 실제 import 규칙을 문서화합니다. 페이지에서만 쓰는 코드는 페이지에 둘 수 있으며, 별도 슬라이스로 나누려면 재사용이나 역할 분리의 이유가 있어야 합니다. 경계를 바꿀 때 [기능 단위 경계](../references/architecture/feature-slice-boundary/feature-slice-layering.ko.md)와 [공개 API 검사](../references/architecture/feature-slice-boundary/slice-public-api-checks.ko.md)를 참고하세요. 다른 구조는 [경계 선택 기준](../references/architecture/boundary-review/fsd-ddd-fit-matrix.ko.md)에서도 다룹니다.

## 바뀔 수 있는 결정의 예시

다음은 한 프로젝트가 선택할 수 있는 결정입니다. AAPB가 요구하는 구조는 아닙니다.

```markdown
# 프론트엔드 모듈 경계

상태: 채택
범위: 브라우저 애플리케이션

라우트는 화면을 조합한다. 각 기능은 UI, 로컬 상태와 API 어댑터를 담당한다.
기능마다 작은 공개 진입점을 제공하며 호출부는 내부 파일을 직접 import하지 않는다.
공유 코드는 기능별 업무 규칙 없이 UI 기본 요소와 통신 유틸리티를 제공한다.

이유: 대부분 한 기능 안에서 변경되며 애플리케이션은 함께 배포한다.
예외: 이전 설정 화면은 이전 기간에 공유 저장소를 계속 사용한다.
설정 화면이 기능별 상태 관리로 옮겨가면 예외를 제거한다.

검증: 저장소의 import 경계 검사와 영향을 받는 상호작용 테스트를 실행한다.
재검토 조건: 별도 배포나 반복되는 기능 간 상태 공유에 다른 경계가 필요해질 때.
```

예시를 적용할 때는 실제 모듈 이름과 기존 명령을 적습니다. 아직 정하지 않은 결정에는 제안임을 표시하세요. 결정이 바뀌면 채택한 문서를 갱신하고, 프로젝트의 이력 보관 방식에 따라 이전 이유와 새 결정의 연결을 남깁니다. import 제한 설정이 있다면 코드와 함께 검증합니다.

## 부트스트랩이 하는 일

프로젝트 폴더에서 실행합니다.

```sh
ai-agent-playbook bootstrap --dry-run
ai-agent-playbook bootstrap
```

기록이 없을 때 CURRENT.md와 관리 파일 두 개를 만듭니다. 소스 폴더 생성, FSD 선택, 스택 프로필 설치, 루트 AGENTS.md 생성·교체는 하지 않습니다. AAPB 스킬 프로필은 프로젝트 아키텍처와 별개로 참고 지침을 선택합니다.

프로젝트를 살핀 뒤 루트 지침이 필요하면 [프로젝트 지침 템플릿](../templates/agents/AGENTS.ko.md)을 조정해 사용합니다. 아키텍처 결정도 도움이 될 때 기존 문서 위치에 둡니다. `.ai-agent-playbook/decisions/architecture.md`를 만들었다면 CURRENT.md에서 `decisions/architecture.md`로 연결합니다. 프로젝트 루트의 `docs/architecture.md`를 쓴다면 링크는 `../docs/architecture.md`입니다. 문서를 먼저 만들고 링크를 추가하세요.

기존 프로젝트는 현재 기록과 아키텍처를 계속 사용할 수 있습니다. [기존 저장소 적용](existing-repository-bootstrap.ko.md)과 [기록 구조](structured-playbook-layout.ko.md)를 참고하세요.
