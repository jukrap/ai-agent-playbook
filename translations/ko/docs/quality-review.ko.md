# 디자인·UI·문서·코드 품질 검토

검토 대상마다 필요한 근거가 다릅니다. 하나의 “AI스러움” 점수만으로 제품에 맞는지, 기존 동작을 지켰는지 알 수는 없습니다. 해당 작업에 맞는 검토를 선택하고 작성자나 제품의 의도를 먼저 확인합니다.

## 검토 대상 고르기

| 대상 | 사용할 지침 | 확인할 근거 |
| --- | --- | --- |
| 디자인 방향 | `design-brief-direction` | 목적, 사용자, 브랜드 참고 사례, 정보 밀도, 구현 제약 |
| 기존 UI | `ui-polish` | 실제 화면, 상호작용 상태, 접근성, 사용자 과제 수행 |
| 한국어·영어 문서 | `natural-writing-humanization` | 의미, 수치, 명령, URL, 용어, 문체, 의도한 강조 |
| 코드 구조 | 선택형 `quality/cleanup-ai-slop` 참고 자료 | 공개 동작, 불필요한 추상화, 중복, 관련 테스트 |

도구 연결은 선택한 디자인·문서 도구의 기능별 지침을 따릅니다. 소설의 승인된 문체, 인물 말투, 후보 승인 절차는 집필 제품에서 관리합니다. 일반 문서 스킬로 원고 변경을 허용하지 않습니다.

## 디자인과 실제 UI 검토

화면을 바꾸기 전에 실제 사용 흐름과 보존할 요소를 적습니다. 정보가 많은 운영 표와 브랜드 표현이 중요한 행사 페이지는 다른 디자인이 필요할 수 있습니다. 카드, 그라데이션, 글꼴, 비대칭 배치도 의도한 선택일 수 있습니다.

필요한 경우 일반·로딩·빈 결과·오류·비활성·포커스 상태를 확인합니다. 주요 화면 너비와 키보드 조작을 비교하세요. 소스의 정적 신호는 후보를 찾는 데 쓰고, 수정 필요성은 실제 화면과 제품 목적에 맞는지로 판단합니다.

```sh
aapb qa ui-genericity-scan "<project>" --root src --max-files 20 --json
```

이 명령은 선택한 텍스트를 읽으며 앱을 렌더링하지 않습니다. 화면과 상호작용은 프로젝트의 브라우저 도구로 확인하세요. 코드 정리 결과와 시각적 취향 판단은 따로 기록합니다.

## 독자를 기준으로 문서 편집하기

먼저 누구를 위한 문서인지, 무엇을 할 수 있게 해야 하는지 확인합니다. 초보자 안내에는 용어, 실행 순서, 예상 결과, 복구 방법이 필요합니다. 명령어 참조에는 문법과 범위가 필요합니다. 스킬 지침이 짧아졌다고 이런 사람용 안내까지 한 문단으로 줄여서는 안 됩니다.

보호할 정보와 의도한 문체를 유지하세요. 예를 들어 제한 시간 `30`초, 정확한 명령, URL은 두고 주변 설명을 쉽게 고칩니다. 한국어에서는 설명 없는 혼용어를 풀어 쓰되 실제 필드와 명령 이름은 유지합니다. 존댓말, 목적이 있는 반복, 브랜드 표현, 언어별 탐색 구성을 기계적으로 제거하지 않습니다.

큰 재작성에서는 선택형 검사가 정보 변경 후보를 찾는 데 도움이 될 수 있습니다.

```sh
aapb writing fidelity-check "<project>" --before docs/before.md --after docs/after.md --lang auto --json
aapb writing naturalness-check "<project>" --path docs/after.md --lang ko --engine js --json
```

실제 수정 전·후 파일을 먼저 준비하세요. 결과에 나온 문장은 문맥과 함께 읽어야 합니다. 어느 검사도 의미 보존이나 작성 주체를 인증하지 않습니다. 일반적인 편집마다 CLI 검사나 점수표를 만들 필요는 없습니다.

## 코드 동작은 별도로 검토하기

래퍼나 추상화가 필요한 계약을 제공하는지 확인한 뒤 제거합니다. 반환값, 오류 처리, 순서, 부수 효과, 공개 인터페이스처럼 관찰 가능한 동작을 살펴보세요. 실제 회귀를 잡을 수 있는 테스트를 고릅니다. 코드가 짧아졌다는 사실만으로 동작이 좋아졌다고 판단하지 않습니다.

## 유용한 검증 근거 남기기

보존한 것, 바꾼 것, 확인 방법, 미검증 사항을 적습니다. 소규모 비교는 입력, 작업 제약, 모델 설정, 완료 기준을 같게 둡니다. 정보 보존, 작업 적합성, 과잉 교정, 관측한 실행 비용은 구분합니다. 다섯 사례만으로 일반적인 성능 향상이나 구독 비용 절감을 주장하지 않습니다. [검증 보고서](verification.ko.md)를 참고하세요.
