# 일반적인 UI 검토

일반적으로 보이는 시각 표현을 보편적인 스타일 금지 규칙이 아니라 제품 적합성 문제로 검토합니다.

## 작업 흐름

1. 제품 유형, 사용자의 핵심 작업, 대상 화면 크기, 기존 디자인 시스템과 브랜드 제약을 확인합니다.
2. 정적 코드 신호를 결함으로 단정하기 전에 실제 렌더링을 봅니다. `aapb qa ui-genericity-scan <target> --json`은 검토 후보를 찾는 용도로만 사용합니다.
3. 반복되는 카드, pill, gradient, glass, glow, 큰 radius, 통계 블록, hover transform, kicker, 마케팅 문구가 작업 위계를 돕는지 확인합니다.
4. 의도적인 브랜드 표현과 기존 컴포넌트를 보존합니다. 작업 집중도, 위계, 밀도, 신뢰성을 높이는 가장 작은 일관된 변경을 권장합니다.
5. 이름을 명시한 화면 크기에서 변경된 화면을 확인하고 이미지나 영상 근거를 남깁니다. 정적 검사를 통과한 것만으로 완료 증거가 되지는 않습니다.

## 경계

- 신뢰하기 어려운 코드 구조 정리는 `cleanup-ai-slop`을 사용합니다. 이 스킬은 시각 디자인 검토가 아닙니다.
- 방향이 정해진 뒤 보이는 구현을 다듬을 때는 `ui-polish`를 사용합니다.
- 제품의 시각 방향 자체가 없으면 `design-brief-direction`을 사용합니다.
- 스크린샷이나 참고 제품을 비교해야 하면 `design-reference-analysis`를 사용합니다.
- 문장 어조는 `natural-writing-humanization`을 사용합니다. 여기서는 UI 문구가 위계나 제품 구체성에 영향을 줄 때만 검토합니다.
