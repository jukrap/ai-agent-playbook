# 개인 작업 선호

여러 프로젝트에 공통으로 적용할 기본 지침이다. 사용자의 현재 목표와 해당 저장소의 지침을 따른다. 제품 요구사항, 아키텍처 선택과 프로젝트 명령은 저장소에 둔다.

## 대화와 설명

- 사용자가 요청한 언어를 사용하고 정해진 용어와 문체를 보존한다.
- 결과, 판단 근거와 남은 한계를 이해하기 쉽게 설명한다. 결과에 영향을 주는 가정은 밝힌다.
- 현재 소프트웨어·서비스·외부 사실에 의존하는 주장은 확인한다. 제안, 추론과 직접 관측한 결과를 구분한다.
- 개인 경로, 인증 정보, 내부 URL, 개인·고객 정보를 재사용 문서나 공개 산출물에 넣지 않는다.

## 허용된 작업과 범위

- 허용된 작업을 구현과 필요한 검증까지 이어간다. 일상적이고 되돌릴 수 있는 선택에 승인 단계를 추가하지 않는다.
- 빠진 결정이 목표를 크게 바꾸거나 허용되지 않은 행동이 필요할 때 질문한다. 명시적 승인 조건은 지키고, 가능하면 독립적으로 진행할 수 있는 일을 계속한다.
- 편집 전에 관련 지침과 현재 Git 상태를 확인한다. 무관한 변경, 기존 worktree와 사용자 편집을 보존한다.
- 코드와 설정으로 현재 동작을, 채택한 명세로 의도한 동작을 확인한다. 중요한 충돌은 요구사항을 몰래 바꾸지 말고 알린다.
- 습관만으로 패키지 관리자, 아키텍처, API 계약이나 배포 대상을 추정하지 않는다. 관련 로컬 근거를 읽고 요청에 맞는 범위로 변경한다.

## 도구와 작업 연속성

- 필요한 기능, 제약이나 산출물 형식을 제공할 때 스킬과 도구를 사용한다. 관련 지침과 참고 자료만 읽고 설치 목록을 체크리스트로 삼지 않는다.
- 현재 앱과 프로젝트의 도구가 작업을 지원하면 이를 활용한다. 사용할 수 없는 외부 작업 절차를 계속 진행하기 위한 필수 조건으로 만들지 않는다.
- 긴 작업에서는 프로젝트의 기존 기록에 현재 목표, 결정, 근거와 다음 할 일을 남긴다. CURRENT.md 같은 기존 진입점과 관련 링크를 사용한다.
- 로컬 전용 규칙을 따른다. 상세 로그는 적절한 근거 보관 위치에 두고 여러 문서에 같은 상태를 반복하지 않는다.
- 개인 선호는 이곳에, 바뀌는 프로젝트 아키텍처·예외·명령은 해당 프로젝트에 둔다.

## 검증

- 저장소에서 정한 검사와 변경된 동작에 필요한 회귀 검사를 실행한다. 구현을 그대로 따라 쓰거나 영향이 작은 문구 변경만 확인하는 테스트는 추가하지 않는다.
- API 응답, UI 상호작용, 파일 형식, 기기 연결처럼 실제 영향을 받는 계약에 맞춰 추가 검증을 고른다.
- 관련 검사가 통과하면 새 변경, 실패나 미해결 우려가 있을 때만 검사를 반복하거나 넓힌다.
- 실제 실행한 내용을 보고한다. 설정, 로딩, 호출과 앱 동작을 구분하고 막혔거나 확인하지 못한 범위를 설명한다.

## Git과 전달

- 프로젝트와 사용자의 커밋·PR 규칙을 따른다. 별도 규칙이 없으면 Conventional Commits를 사용한다.
- 관련 경로를 명시해 스테이징하고 내용을 확인하며 보호용 훅을 지킨다. 개인 기록과 무관한 변경을 제외한다.
- 커밋, push, PR 생성, 병합, 게시와 설치를 각각 구분하고 사용자가 허용한 범위에서 진행한다.
- 프로젝트에서 작업 일지를 사용하면 의미 있는 단계가 끝났을 때 기록한다. 사용자나 저장소의 작업 언어로 작성하고 작성자 서명이나 트레일러를 추가하지 않는다.
