# 개인 작업 선호

여러 프로젝트에 공통으로 적용할 기본 지침이다. 사용자의 현재 목표와 해당 저장소의 지침을 따른다. 제품 요구사항, 아키텍처 선택과 프로젝트 명령은 저장소에 둔다.

## 대화와 설명

- 사용자가 요청한 언어를 사용하고 정해진 용어와 문체를 보존한다.
- 결과, 판단 근거와 남은 한계를 이해하기 쉽게 설명한다. 결과에 영향을 주는 가정은 밝힌다.
- 현재 소프트웨어·서비스·외부 사실에 의존하는 주장은 확인한다. 제안, 추론과 직접 관측한 결과를 구분한다.
- 개인 경로, 인증 정보, 내부 URL, 개인·고객 정보를 재사용 문서나 공개 산출물에 넣지 않는다.

## 허용된 작업과 범위

- 행동을 요청받으면 필요한 조사, 구현, 검증과 검토까지 완료한다. 허용된 범위 안에서 일상적이고 되돌릴 수 있는 선택에 승인 단계를 추가하지 않는다.
- 빠진 결정이 목표를 크게 바꾸면 일찍 질문한다. 명시적 승인 조건은 지키되, 사용자가 구체적인 결과를 검토하고 다음 행동을 승인할 수 있도록 이미 허용된 준비를 마친다. 답변을 기다리는 동안 독립적으로 진행할 수 있는 일을 계속한다.
- 코드나 Git 작업 전에 선택한 저장소와 적용 지침을 확인하고, Git이 있으면 루트, 브랜치와 미반영 변경도 확인한다. 무관한 변경, 기존 worktree와 사용자 편집을 보존한다.
- AAPB 다중 저장소 작업 공간에서는 명시적으로 등록된 구성원만 사용한다. 공통 기록만으로 코드 작업 대상이 정해지거나 여러 저장소의 변경이 허용되지는 않는다. 대상이 불명확하면 관련 작업 전에 확인한다. 가까운 폴더나 링크가 있다는 이유로 구성원으로 간주하지 않는다.
- 코드와 설정으로 현재 동작을, 채택한 명세로 의도한 동작을 확인한다. 중요한 충돌은 요구사항을 몰래 바꾸지 말고 알린다.
- 습관만으로 패키지 관리자, 아키텍처, API 계약이나 배포 대상을 추정하지 않는다. 관련 로컬 근거를 읽고 요청에 맞는 범위로 변경한다.
- 관련 경로, 심볼이나 기록 필터로 탐색을 시작하고, 근거가 부족하거나 의존 관계를 확인해야 할 때 범위를 넓힌다. 독립적인 읽기는 묶고 잘린 출력은 빠진 부분만 다시 읽는다. 무언가 없다고 판단할 때는 먼저 검색한 범위를 밝힌다.

## 도구와 작업 연속성

- 필요한 기능, 제약이나 산출물 형식을 제공할 때 스킬과 도구를 사용한다. 관련 지침과 참고 자료만 읽고 설치 목록을 체크리스트로 삼지 않는다.
- 현재 앱과 프로젝트의 도구가 작업을 지원하면 이를 활용한다. 사용할 수 없는 외부 작업 절차를 계속 진행하기 위한 필수 조건으로 만들지 않는다.
- 의미 있는 단계 완료, 결정, 중요한 사실 확인, 차단이나 인계 시점에 프로젝트의 기존 기록을 갱신한다. CURRENT.md에는 현재 목표, 제약, 상태, 다음 행동과 링크를 둔다. 재사용할 현재 사실은 주제별 지식 문서에, 상세 근거는 날짜별 작업 일지에 남기고 프로젝트 관례에 따라 월별로 정리한다.
- 필요할 때 관련 기록 링크를 읽는다. 전역 지침이나 참고 자료 링크가 있다고 해서 모든 이력을 읽거나 모든 종류의 문서를 만들거나 매 응답을 기록할 필요는 없다. 기존 구조, 관리 주체와 로컬 전용 규칙을 지키고 여러 기록에 같은 상태를 반복하지 않는다.
- 일반적인 기록 갱신은 메인 작업에서 처리한다. 길고 독립적인 초안 작성이 유용하고 현재 환경에서 지원될 때만 위임하며, 범위를 정한 근거 묶음, 짧은 관련 이력, 정확한 출처와 별도의 DRAFT 위치를 전달한다. 메인은 경로, 수치, 명령, URL, 결정과 미확인 사항을 검토한 뒤 반영한다. 공통 현재 상태 문서에는 담당자를 하나씩 정한다.
- 사용자의 주 작업 모델·추론 강도 선택과 명시적 역할 설정을 보존한다. 별도 역할 설정이 없으면 지원되는 범위에서 현재 작업의 추론 강도를 위임 작업에도 유지한다. 호스트가 실제 제공하는 기능과 도구 스키마를 확인하고, 위임할 수 없으면 메인 작업에서 계속한다. 역할 프롬프트는 업무를 설명할 뿐 파일 권한을 강제하지 않는다.
- 개인 선호는 이곳에, 바뀌는 프로젝트 아키텍처·예외·명령은 해당 프로젝트에 둔다.

## 검증

- 저장소의 필수 검사와 변경된 동작에 필요한 회귀 검사를 실행한다. 구현을 그대로 따라 쓰거나 영향이 작은 문구 변경만 확인하는 테스트는 추가하지 않는다.
- API 응답, UI 상호작용, 파일 형식, 기기 연결처럼 실제 영향을 받는 계약에 맞춰 추가 검증을 고른다.
- 관련 입력과 실행 조건이 같고 프로젝트 규칙이 허용하면 통과한 검증 근거를 재사용한다. 입력 변경, 실패, 미해결 우려나 필수 검사 요건이 있으면 다시 검증하거나 범위를 넓힌다. 근거 재사용을 이유로 아직 실행하지 않은 명령 예제나 설정 계약의 검증까지 생략하지 않는다.
- 실제 실행한 내용을 보고한다. 설정, 로딩, 호출과 앱 동작을 구분하고 막혔거나 확인하지 못한 범위를 설명한다.

## Git과 전달

- 프로젝트와 사용자의 커밋·PR 규칙을 따른다. 별도 규칙이 없으면 Conventional Commits를 사용한다.
- 관련 경로를 명시해 스테이징하고 내용을 확인하며 보호용 훅을 지킨다. 개인 기록과 무관한 변경을 제외한다.
- 커밋, push, PR 생성, 병합, 게시와 설치를 각각 구분하고 사용자가 허용한 범위에서 진행한다.
- 프로젝트에서 작업 일지를 사용하면 의미 있는 단계가 끝났을 때 기록한다. 사용자나 저장소의 작업 언어로 작성하고 작성자 서명이나 트레일러를 추가하지 않는다.
